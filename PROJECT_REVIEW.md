# Оценка проекта и что стоит улучшить

## 1. Общая оценка

Проект уже имеет рабочую основу: есть движение игрока, триггеры, магазин, крафт, прогресс в `PlayerPrefs`, переход между сценами и базовая логика накопления ресурсов. Это хороший прототип/игровой MVP, который можно играть и проверять в редакторе.

Но сейчас проект ещё очень "пластичный" в плане архитектуры: есть несколько мест, где логика размазана по разным классам и в будущем это начнёт усложнять добавление новых механик, систем и контента.

Оценка по текущему состоянию:

- Состояние проекта: рабочий прототип, но ещё не финальная архитектура
- Сильная сторона: понятная механика и простая логика развития
- Основной риск: рост количества систем без нормальной структуры
- Плюс: есть база, на которой можно качественно масштабировать проект

---

## 2. Что уже сделано хорошо

### 2.1. Простая и понятная механика прогресса

В проекте уже есть понятные игровые значения:

- монеты
- батарея дрона
- корпуса
- взрывчатка
- прогресс апгрейда дрона

Это хороший базовый слой для системы прогресса. С точки зрения геймдизайна логика достаточно понятна.

### 2.2. Есть базовая связка между системами

Механики вроде:

- подбирание предметов
- покупка в магазине
- крафт
- смерть/перезапуск уровня
- сохранение данных

уже связаны между собой, что важно для MVP. Это значит, проект уже проходит проверку на "играбельность в базовом виде".

### 2.3. Прогресс сохранён в PlayerPrefs

Для простого прототипа это нормальный вариант. Он быстрый в реализации и позволяет сохранить состояние между сессиями.

---

## 3. Что стоит улучшить в первую очередь

### 3.1. `GameManager` слишком перегружен

Сейчас `GameManager` отвечает сразу за несколько разных вещей:

- UI панели
- переменные игрока
- сохранение и загрузку
- прогресс и апгрейд
- загрузка сцен
- сброс данных

Это нарушает принцип единственной ответственности. Такой класс со временем станет "God Object" — монолитом, в который будет очень сложно добавлять новые фичи.

Что лучше сделать:

- вынести сохранение в отдельный `SaveSystem`
- вынести прогресс игрока в `PlayerProgress` или `PlayerStats`
- оставить `GameManager` только как общую управляющую точку, а не как склад всех данных

### 3.2. Смешаны разные уровни ответственности

В разных классах есть логика, которая по смыслу должна быть отделена:

- `Triggers` отвечает за коллизии и ввод ресурсов
- `ShopManager` отвечает за покупку
- `CraftManager` отвечает за крафт
- `GameManager` отвечает за хранилище и UI

Это допустимо для маленького проекта, но уже сейчас заметно, что часть логики начинает дублироваться. Например, покупки, проверка денег, изменения ресурсов и анимация/звук разнесены по разным местам.

### 3.3. Использование `FindAnyObjectByType` в нескольких местах

Этот вызов удобен для быстрого прототипа, но плох для масштабируемого проекта.

Проблемы:

- неявное зависимое связывание
- хрупкость при смене сцен
- ухудшение читаемости и предсказуемости
- возможность получить не тот объект, если в сцене несколько одинаковых компонентов

Что лучше:

- использовать `Singleton` для `GameManager` или `RuntimeInitializeOnLoad`
- передавать зависимости через `SerializeField`/ссылки
- использовать более явную инициализацию между системами

### 3.4. Слишком много "магических строк" и хардкода

Есть строки вроде:

- `"Coin"`
- `"Batt"`
- `"Corps"`
- `"Expl"`
- `"Fpv_drone"`
- `"NEED 0/10 FPV DRONE"`

Это всё хрупко. В будущем будет сложно:

- менять ключи
- отслеживать структуру сохранений
- мигрировать данные
- поддерживать разные версии игры

Лучше завести:

- `SaveKeys` либо `PlayerPrefsKeys`
- отдельный класс констант
- систему версий сохранений

### 3.5. Данные и UI напрямую связаны

В `GameManager` значения обновляются не только в памяти, но и сразу в `Text` полях. Это можно считать рабочим вариантом, но архитектурно это не очень хорошо.

Проблема:

- UI и состояние смешаны
- сложнее переиспользовать логику в другом интерфейсе
- сложнее тестировать

Лучше:

- хранить данные отдельно
- обновлять UI через отдельный `UIManager` или через подписки на события
- получать значения из модели, а не из виджетов

## 4. Где стоит переделать структуру

### 4.1. Выделить систему прогресса

Нужно вынести логику в отдельный компонент, например:

- `PlayerProgress`
- `GameData`
- `ProgressService`

Там должна храниться модель прогресса:

- coins
- battery
- corps
- explosives
- fpvDroneLevel

Плюс методы:

- AddCoins
- SpendCoins
- AddBattery
- AddCorps
- Save
- Load

Так будет проще понимать, что именно хранится и что это за данные.

### 4.2. Выделить сервис сохранения

Сейчас хранение смешано с логикой игрока. Лучше сделать отдельный сервис:

- `SaveService`
- `ISaveService`
- `PlayerPrefsSaveService`

Потом можно будет заменить `PlayerPrefs` на:

- JSON
- ScriptableObject
- SQLite
- облако / сеть

без правки игровой логики.

### 4.3. Сделать систему UI

Сейчас панели и тексты напрямую управляются из разных классов. Лучше сделать одну систему UI:

- `UIManager`
- `PanelsController`
- `HudView`

Так будет проще:

- переключать интерфейс
- обновлять панели
- скрывать/показывать состояния
- развивать меню и диалоговые экраны

### 4.4. Разделить игровые события и сценарные переходы

В `CraftManager.TryCraft()` логика сейчас делает сразу несколько вещей:

- проверка ресурсов
- списание ресурсов
- повышение прогресса
- запуск звука
- проверка условия победы
- сброс данных
- переход на следующий уровень

Это слишком много ответственности за один метод. Это место очень удобно для дальнейших багов.

Нужно разделить на:

- проверку крафта
- применение результата крафта
- проверку победы / прогресса уровня
- обработку завершения уровня
- загрузку следующей сцены

## 5. Где в дальнейшем будет сложно изменять структуру

### 5.1. `GameManager` как центральный "божественный" объект

Это главный риск. Чем больше будет новых механик, тем больше `GameManager` будет разрастаться. Он станет местом, куда всё сваливается: ресурсы, UI, сцены, прогресс, диалоги, события, музыка, логика маршрутов и т.д.

### 5.2. `PlayerPrefs` как единственный способ хранения

На раннем этапе это нормально, но по мере роста игры появятся:

- сессии
- разные save-slots
- игровые настройки
- музыка/звук
- прогресс по уровням
- сезонные системы
- профиль игрока

Тогда прямой набор ключей и один `GetInt`/`SetInt` станет очень неудобным и опасным.

### 5.3. Использование тегов как основного способа идентификации объектов

В `Triggers` используется `switch (other.tag)`. Это рабочий вариант для прототипа, но плохой для расширения:

- теги легко ломаются
- трудно отследить все варианты
- нельзя удобно расширять типы объектов
- при многих объектах сцены логика становится хаотичной

Лучше:

- использовать `enum` или типы предметов
- сделать `PickupType`
- сделать программируемые `ScriptableObject` сущности для ресурсов/предметов

### 5.4. Пустая заготовка в `SpawnObjecttAwake`

Файл `SpawnObjecttAwake.cs` пока содержит только комментарии. Это нормально для незаконченной идеи, но именно такие места часто становятся точками накопления "непонятной логики". Их лучше либо быстро закрыть концепцией, либо отложить, чтобы не создавать ложное ощущение готовой системы.

### 5.5. Система прогресса без валидации и сценарного контекста

Сейчас значения просто инкрементируются и декрементируются. Нет ограничений по:

- минимальным/максимальным значениям
- проверкам на отрицательные числа
- контексту расчёта пула ресурсов
- правилам уровня/прогресса

Это может привести к багам, когда значения уйдут в некорректное состояние и их дальше будет сложно отлаживать.

## 6. Что ещё стоит учитывать на будущее

### 6.1. Ввести состояния и сценарии игры

Сейчас логика игры выглядит как набор функций, но не как система состояний. Например:

- старт уровня
- в игре
- пауза
- смерть
- победа
- переход на новый уровень
- завершение игры

Эти состояния лучше описывать через:

- `enum GameState`
- `StateMachine`
- отдельный `LevelController`

Это существенно упрощает поддержку и расширение.

### 6.2. Декомпозиция на отдельные подсистемы

Для роста проекта желательно быстро разделить проект на такие блоки:

- Core / bootstrap
- Player
- Progress
- Inventory
- Shop
- Craft
- UI
- Save / Data
- Level / Scene Flow
- Audio / VFX

Тогда каждая система будет иметь свою зону ответственности.

### 6.3. Тестировать поведение, а не только визуально

Пока проект выглядит как прототип, можно обойтись без полноценного тестирования, но уже сейчас стоит заранее приучать себя к проверке:

- корректность сохранений
- правильность списания ресурсов
- корректность крафта
- защита от отрицательных значений
- проверка перехода между сценами

Иначе появится много "ручных проверок" и сложных воспроизводимых багов.

---

## 7. Рекомендации по порядку улучшений

### Приоритет 1: архитектура данных

1. вынести логику прогресса в отдельный класс
2. вынести сохранение в отдельный сервис
3. сделать единые константы для ключей сохранения

### Приоритет 2: очистка зависимостей

1. убрать `FindAnyObjectByType` там, где это можно заменить явной ссылкой
2. нормализовать инициализацию через `Awake`/`Start`
3. сделать более явные связи между системами

### Приоритет 3: чёткая структура логики

1. разделить `GameManager` на задачи
2. выделить `UIManager`
3. сделать отдельный `LevelProgressController`

### Приоритет 4: масштабирование и подготовка к развитию

1. добавить состояния игры
2. выстроить систему предметов и ресурсов
3. подготовить модель данных под будущие уровни, магазины, апгрейды и прогресс по игре

## 8. Итоговая оценка

Проект уже выглядит как рабочий и интересный prototype с понятной игровой идеей и базовой механикой. По сути, это хороший фундамент для дальнейшей разработки.

Но сейчас есть два главных ограничения:

- архитектура ещё слишком "связанная" и монолитная
- часть системы проектируется под быстрый прототип, а не под долгосрочное расширение

Если проект будет расти, то главная задача на ближайшем этапе — не добавлять механики в лоб, а стабилизировать структуру данных и разделить ответственности между системами.

То есть:

- сейчас проект уже можно считать "играбельным MVP"
- но ещё не стоит считать его "финальной архитектурой"
- ближайшие улучшения должны концентрироваться на данных, модульности и уменьшении связности между классами

Это важный этап: если его не сделать сейчас, потом рефакторинг будет гораздо дороже и сложнее.

---

## 9. Краткий вывод

Если говорить коротко:

- проект хороший как прототип и как идея
- архитектура требует упорядочивания
- `GameManager` — главный кандидат на рефакторинг
- `PlayerPrefs` — приемлемо на старте, но слабое место для роста
- теги, прямые UI-связи и монолитная логика станут проблемой в будущем

Это не критика, а нормальная оценка раннего проекта: базовая идея уже есть, теперь главное — сделать структуру устойчивой к дальнейшему развитию.
